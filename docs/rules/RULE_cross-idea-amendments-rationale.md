# RULE_cross-idea-amendments — Rationale + Anti-Patterns

## Why this rule exists

The cost of preserving a shipped decision past its useful life is higher than the cost of revising it cleanly. A sprint cohort with multiple foundation-tier IDEAs (toast surface, modal primitives, drawer system, etc.) inevitably surfaces relationships that weren't visible when each IDEA shipped in isolation. Forcing every cross-IDEA touch through a separate "supersede + new IDEA" cycle adds ceremony that discourages real improvements.

The flexibility-first framing preserves the *learning loop* — when a downstream IDEA discovers that an upstream IDEA's choice no longer fits, the right response is to amend the upstream choice, not to layer workarounds on top of it. The bidirectional documentation rule keeps the trail honest so future readers can reconstruct *why* the upstream changed.

## Concrete examples of when the rule applies

- A modal-primitives IDEA bumps the z-index in the toast IDEA's `_toast.scss` — the relationship between the two overlays only becomes clear once both are designed together.
- A new-table-component IDEA tightens a constraint in the row-renderer IDEA's template — performance regression caught only at integration time.
- A new-translation-flow IDEA renames a translation-map function originally defined in the i18n-extraction IDEA — naming evolved as the surface grew.

Does *not* apply to:

- Bug fixes inside the original IDEA's files made by the original IDEA's author within the original PR cycle. That's normal in-PR iteration.
- Routine sustaining work (dependency upgrades, security patches) that rolls through every file regardless of which IDEA originally authored it.

## The inline-comment step does not apply to content-hashed files

Step 2 of the contract (refresh the amended file's inline marker) assumes the file is plain source. Some files are **hashed after they are applied**, and a comment-only edit changes the hash:

- **Applied DB migrations** under a checksumming runner (Flyway, Liquibase, a house runner that records a per-database checksum in its ledger). Editing the file — even a header comment — makes every later `migrate` on every deployment that already applied it print a drift warning (or refuse to run), forever, on a file that is otherwise inert. Field case: a follow-on IDEA added `(amended IDEA-NNN: …)` to the header of the migration that created the table it was altering; the next `migrate` answered `WARNING — checksum drift on <stem> (applied file edited since apply; not re-run)`. The marker was reverted in the same PR; the earlier sibling IDEA that altered a *different* table had — correctly — never touched that table's migration file either.
- Signed or locked artefacts (lockfiles regenerated by a tool, vendored bundles with an integrity manifest, generated specs a drift test compares byte-for-byte) — same shape: the edit is a verification failure, not a note.

For these files the bidirectional trail still holds, through the other three steps: the **new** migration's header names the table and the IDEA it amends, the commit trailer carries `Amends IDEA-MMM <file>`, and the `/wrap` backref lands in the amended IDEA's archive. Nothing is lost except the in-file grep hit — and a reader grepping the old migration for the column will find it only in the new one anyway, which is where the column is defined.

**The data a hashed stem seeded is amendable even though the stem is not.** When a later IDEA makes a *row* the earlier stem wrote false — an operator-facing description that said "the listed price is the minimum" once a configurable minimum exists — the fix is one more statement in the **new** stem: `UPDATE … SET <text> = <new> WHERE <key> = … AND <text> IN (<every text the seeds have ever written>)`. Equality on the seeded texts is what keeps an operator-written value untouched (the same convergence contract the original seed used); the down-file restores the latest seeded text where the value equals the new one; the header names the stems whose data it amends and the commit trailer carries `Amends IDEA-MMM <stem> (seeded text)`; the walk proves both directions and the operator-edited case. Field case and the surrounding bound-semantics decisions: `skills/plan/references/CONFIGURED_BOUND_OVER_A_DERIVED_FLOOR.md` § 6.

## Building the amended-IDEA list from the diff

Steps 1 and 3 need the full list of amended IDEAs. Write it from the diff, never from memory. Recall gives the IDEAs
whose *idea* you were thinking about. It misses the ones whose *files* you touched mechanically: a test helper flipped
in a sweep, a harness file, a doc an earlier IDEA created.

```bash
for f in $(git diff --name-only origin/<default>...HEAD); do
  printf '%s\t%s\n' "$f" "$(git log --diff-filter=A --format=%s -- "$f" | tail -1)"
done
```

The creating commit's subject names the owning IDEA. Read the file's own header comment too, because ownership can
move: a later IDEA rewrote the file. Three traps, all field-observed on one IDEA that touched 16 others' files:

- **A file created by a non-IDEA PR is not an amendment.** Examples: a docs PR, a release-prep PR, a hotfix.
  Attributing it to the IDEA "it feels like" plants a false backref in that IDEA's archive. An independent review
  caught exactly this: a runbook created by a plain docs PR was credited to the cut-over IDEA.
- **The first commit's `Amends` trailer is usually short.** It lists the IDEAs you meant to change; the mechanical
  sweep amends more. Rewriting pushed history is worse than an incomplete trailer, so complete the list in a later
  commit's trailer ("the full list for this PR, completing <sha>'s"). Repeat it in the execution record and the PR text,
  where `/wrap` reads it for the backrefs.
- **Backref sections have a direction.** Where an archive README keeps both "Amended" (what this IDEA changed in
  others) and "Amended later" (later IDEAs that changed this one), a backref goes under "Amended later". Before
  appending, check that the section you append to is the last one and has that meaning. Misfiled bullets look right
  in isolation.

## Anti-patterns

- ❌ **Re-opening the original IDEA's branch** to make the change. The original IDEA is shipped; the change belongs in the current IDEA's commits.
- ❌ **Filing a "supersede" relationship** on the original IDEA. Amendments aren't supersessions — the original IDEA's main work is still the canonical implementation; the amendment is a tweak.
- ❌ **Spinning up a new "fix the upstream IDEA" IDEA**. That defers the fix indefinitely (small docs/refactor IDEAs rarely ship). The right place is the IDEA whose work *needed* the upstream change.
- ❌ **Silent amendments** with no commit-message tag, no inline comment refresh, no archive backref. The next reader has no way to discover the amendment exists.
- ❌ **Size caps** ("≤ N lines", "single file only"). The original draft of this rule had bounded the precedent — explicitly retired per user direction: "implemented ideas are not stones".
